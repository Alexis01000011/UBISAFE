# Acceptance Tests — CU-03: Reportar Zona de Riesgo

**Feature:** F5 — RiskFormBottomSheet + MapScreenBuyer/Vendor + RiskZoneService + Backend Safety
**SDD refs:** SDD_FASE4_UBISAFE.md §8.3 · SDD_FASE2_PASO25_UBISAFE.md §5.3.4

---

## Precondiciones

1. Firebase emuladores corriendo:
   ```bash
   firebase emulators:start --project demo-ubisafe
   ```
2. API corriendo (con venv activado):
   ```bash
   cd ubisafe_api
   uvicorn main:app --reload
   ```
3. App en dos instancias (dispositivo físico o dos emuladores).
4. Un usuario autenticado en cada instancia (Usuario A y Usuario B).
5. Ambos usuarios con `MapScreenBuyer` abierto.

---

## S1 — Flujo Normal (Creación y Notificación Multicast)

**Corresponde a:** SDD_FASE4_UBISAFE.md §8.3 Flujo Principal

| # | Actor | Acción | Resultado esperado |
|---|-------|--------|--------------------|
| 1 | Usuario A | Toca el botón FAB (+) de reporte en mapa | Se abre el Bottom Sheet `RiskFormBottomSheet` |
| 2 | Usuario A | Selecciona nivel "HIGH", ingresa amenaza "Asalto" y toca **"Reportar Zona"** | Bottom sheet se cierra con loader. Snackbar de "Enviando reporte..." |
| 3 | Sistema | API `POST /risk-zones` recibe payload | Firestore crea `risk_zones/{id}` con `active: true`. Dispara multicast FCM a todos los tokens (incluyendo Usuario B) |
| 4 | Usuario B | App en primer plano | Recibe FCM `risk_zone_alert`. El `activeRiskZonesProvider` hace refetch de los polígonos del mapa |
| 5 | Usuario B | Observa mapa | Un polígono ROJO (#C62828) de 100m de radio aparece en el mapa inmediatamente |
| 6 | Usuario A | Observa mapa | Un polígono ROJO (#C62828) aparece en su propio mapa |

**Criterio de éxito:** Firestore registra la zona con el nivel correcto. FCM se transmite exitosamente e impacta en la recarga reactiva de los mapas en los dispositivos suscriptos.

---

## S2 — Validación de Duplicados (Bounding Box + Haversine)

**Corresponde a:** Validaciones Backend en `router.py`

| # | Actor | Acción | Resultado esperado |
|---|-------|--------|--------------------|
| 1 | Usuario A | Abre FAB y reporta nueva zona "MEDIUM" cerca de la zona creada en S1 | Bottom sheet envía la solicitud al backend |
| 2 | Sistema | Backend recibe `POST` y evalúa distancia contra la zona activa previa | Distancia < 100m. Retorna `409 Conflict` `{"error": "duplicate_risk_zone"}` |
| 3 | Usuario A | App recibe 409 | Muestra SnackBar rojo: "Ya existe una zona activa en esta área" |

**Criterio de éxito:** El backend bloquea correctamente zonas solapadas y el cliente muestra el error gracefully sin cerrarse.

---

## S3 — Expiración de Zona de Riesgo (Baja lógica)

**Corresponde a:** Flujo `DELETE /risk-zones/{id}` y expiración automática

| # | Actor | Acción | Resultado esperado |
|---|-------|--------|--------------------|
| 1 | Admin | Llama a `DELETE /risk-zones/{id}` (o expira automáticamente el backend tras 24h) | Firestore `active` = false, `expired_at` se puebla |
| 2 | Usuario B | Fuerza recarga del mapa (salir y volver a entrar o recibir nuevo push de otra zona) | El polígono correspondiente desaparece de la vista porque `GET /risk-zones` filtra por `active == true` |

**Criterio de éxito:** El campo `active` marca el borrado lógico y el GET respeta la condición de filtrado activo.
