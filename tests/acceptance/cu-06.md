# Acceptance Tests — CU-06: Validar foco de infección

**Feature:** F7 — ReportValidationModule + ReportDetailScreen  
**SDD refs:** SDD2_FASE4B_UBISAFE.md §9.6.C / §9.6.D  
**Endpoint:** `PATCH /community-reports/{id}/validations`

---

## Precondiciones

1. Firebase emuladores corriendo:
   ```bash
   firebase emulators:start --project demo-ubisafe
   ```
2. API corriendo:
   ```bash
   cd ubisafe_api
   uvicorn main:app --reload
   ```
3. App instalada en **al menos dos dispositivos/instancias** (reporter + validadores).
4. Si se usan dispositivos físicos, `adb reverse` configurado en todos:
   ```bash
   adb reverse tcp:9099 tcp:9099
   adb reverse tcp:8080 tcp:8080
   adb reverse tcp:9000 tcp:9000
   adb reverse tcp:8000 tcp:8000
   ```
5. Tres cuentas de prueba registradas:
   - **Usuario R** (`reporter@test.com`) — quien crea el reporte.
   - **Usuario V1** (`v1@test.com`) — primer validador.
   - **Usuario V2** (`v2@test.com`) — segundo validador.
   - **Usuario V3** (`v3@test.com`) — tercer validador (necesario para promover estado).
6. Todos los usuarios deben tener un perfil en Firestore (`role: "BUYER"` es suficiente).

> **Atajo de configuración:** Crear el reporte directamente vía `curl` o Firestore Emulator UI
> para no depender de SC-01 de CU-05 como prerequisito de cada escenario.
>
> ```bash
> # Crear reporte de prueba via API (autenticado como reporter@test.com):
> curl -X POST http://localhost:8000/community-reports \
>   -H "Authorization: Bearer <reporter_token>" \
>   -H "Content-Type: application/json" \
>   -d '{"threat_type":"animal_muerto","location":{"lat":20.6736,"lng":-103.344}}'
> ```
> Anotar el `id` del reporte devuelto — se usa en todos los escenarios.

## SC-01 — Flujo normal: reporte promovido a `confirmed` (3 votos confirmar)

**Objetivo:** tres usuarios distintos confirman el mismo reporte → `status` cambia a `confirmed`.

| # | Actor | Acción | Resultado esperado |
|---|---|---|---|
| 1 | Usuario V1 | Abre el mapa → ve el marcador del reporte → toca el marcador → toca la info window para abrir `ReportDetailScreen` | Pantalla de detalle muestra tipo "Animal muerto", estado "Pendiente de validación", contadores `Confirmaciones: 0 / Rechazos: 0`. Botones "Confirmar" y "Descartar" visibles |
| 2 | Usuario V1 | Toca **"Confirmar"** | `PATCH /community-reports/{id}/validations` → `200 OK`. Pantalla actualiza contadores: `Confirmaciones: 1`. Spinner desaparece. Botones desaparecen ("Ya votaste en este reporte.") |
| 3 | Usuario V2 | Abre la misma pantalla de detalle | Estado "Pendiente de validación", `Confirmaciones: 1 / Rechazos: 0`. Botones de voto visibles |
| 4 | Usuario V2 | Toca **"Confirmar"** | `Confirmaciones: 2`. Botones desaparecen para V2 |
| 5 | Usuario V3 | Abre la misma pantalla de detalle | Estado "Pendiente de validación", `Confirmaciones: 2` |
| 6 | Usuario V3 | Toca **"Confirmar"** | `PATCH` → `200 OK`. `confirm_count` llega a 3 → API actualiza `status: "confirmed"` en Firestore. Pantalla muestra estado **"Validado"**, `Confirmaciones: 3`. Botones de voto desaparecen ("Este reporte ya no está disponible para votar.") |
| 7 | Usuario V1 | Vuelve al mapa (o refresca) | El marcador del reporte permanece visible. Su snippet ahora dice "Animal muerto · Validado" |

**Verificación en Firestore Emulator UI:**
- `community_reports/{id}.status = "confirmed"`
- `community_reports/{id}.confirm_count = 3`
- `community_reports/{id}.validations` tiene 3 entradas con `verdict: "confirm"`

**Criterio de éxito:** `status: "confirmed"` en Firestore. Pantalla de detalle refleja el estado final sin necesidad de reiniciar la app.

**Verificación:** `community_reports/{id}.status = "dismissed"`, `dismiss_count = 3`.

## SC-03 — Auto-voto bloqueado (403 `reporter_cannot_vote`)

**Objetivo:** el reportero no puede votar en su propio reporte.

| # | Actor | Acción | Resultado esperado |
|---|---|---|---|
| 1 | Usuario R | Abre el mapa → toca su propio marcador → abre `ReportDetailScreen` | Pantalla muestra "No puedes votar en tu propio reporte." Botones "Confirmar" y "Descartar" **no son visibles** |
| 2 | (verificación directa) | Llamar `PATCH /community-reports/{id}/validations` autenticado como reporter | `403 Forbidden` con `detail: "reporter_cannot_vote"` |

**Verificación vía curl:**
```bash
curl -X PATCH http://localhost:8000/community-reports/{id}/validations \
  -H "Authorization: Bearer <reporter_token>" \
  -H "Content-Type: application/json" \
  -d '{"vote":"confirm"}'
# Esperado: 403 {"detail":"reporter_cannot_vote"}
```

**Criterio de éxito:** API devuelve 403. UI no muestra botones de voto. `validations` en Firestore no cambia.

## SC-04 — Doble voto bloqueado (409 `already_voted`)

**Objetivo:** el mismo usuario no puede votar dos veces en el mismo reporte.

| # | Actor | Acción | Resultado esperado |
|---|---|---|---|
| 1 | Usuario V1 | Vota "Confirmar" en el reporte | `200 OK`, `confirm_count: 1`. Pantalla dice "Ya votaste en este reporte." |
| 2 | Usuario V1 | Intenta votar de nuevo vía curl | `409 Conflict` con `detail: "already_voted"` |

**Verificación vía curl (segundo intento):**
```bash
curl -X PATCH http://localhost:8000/community-reports/{id}/validations \
  -H "Authorization: Bearer <v1_token>" \
  -H "Content-Type: application/json" \
  -d '{"vote":"dismiss"}'
# Esperado: 409 {"detail":"already_voted"}
```

**Criterio de éxito:** el segundo voto es rechazado. `validations` tiene exactamente 1 entrada de V1.

## SC-05 — Voto en reporte ya cerrado (409 `report_status_is_*`)

**Objetivo:** no se puede votar en un reporte que ya está en `confirmed`, `dismissed` o `expired`.

**Prerrequisito:** tener un reporte en estado `confirmed` (completar SC-01 primero, o modificar `status` manualmente en Firestore Emulator UI).

| # | Actor | Acción | Resultado esperado |
|---|---|---|---|
| 1 | Usuario V2 (no ha votado antes) | Abre `ReportDetailScreen` del reporte en `confirmed` | Pantalla muestra estado "Validado". Mensaje "Este reporte ya no está disponible para votar." Sin botones de voto |
| 2 | Usuario V2 | Intenta votar vía curl | `409 Conflict` con `detail: "report_status_is_confirmed"` |

**Variante con `expired`:** editar manualmente el campo `status: "expired"` en Firestore Emulator UI y repetir el paso 2.

```bash
curl -X PATCH http://localhost:8000/community-reports/{id}/validations \
  -H "Authorization: Bearer <v2_token>" \
  -H "Content-Type: application/json" \
  -d '{"vote":"confirm"}'
# Esperado: 409 {"detail":"report_status_is_confirmed"}  (o _dismissed / _expired)
```

## SC-06 — Reporte inexistente (404 `report_not_found`)

**Objetivo:** la API responde 404 si el `report_id` no existe.

```bash
curl -X PATCH http://localhost:8000/community-reports/id-que-no-existe/validations \
  -H "Authorization: Bearer <v1_token>" \
  -H "Content-Type: application/json" \
  -d '{"vote":"confirm"}'
# Esperado: 404 {"detail":"report_not_found"}
```

**Criterio de éxito:** 404 sin crash del servidor.

## SC-07 — Concurrencia: dos validadores votan simultáneamente (integridad de transacción)

**Objetivo:** la transacción Firestore (`vote_community_report`) garantiza que dos votos simultáneos no corrompen los contadores.

**Prerrequisito:** reporte en `pending_validation` con `confirm_count: 0`.

| # | Acción | Resultado esperado |
|---|---|---|
| 1 | V1 y V2 envían `PATCH confirm` casi simultáneamente (dos terminales al mismo tiempo) | Ambos reciben `200 OK` |
| 2 | Verificar Firestore | `confirm_count = 2`, `validations` tiene exactamente 2 entradas distintas (no duplicadas). No hay inconsistencias |

**Simulación con dos terminales:**
```bash
# Terminal 1
curl -X PATCH http://localhost:8000/community-reports/{id}/validations \
  -H "Authorization: Bearer <v1_token>" -H "Content-Type: application/json" \
  -d '{"vote":"confirm"}' &

# Terminal 2 (ejecutar inmediatamente después)
curl -X PATCH http://localhost:8000/community-reports/{id}/validations \
  -H "Authorization: Bearer <v2_token>" -H "Content-Type: application/json" \
  -d '{"vote":"confirm"}'
```

**Criterio de éxito:** `confirm_count = 2` (no 1 ni 3). Ambas entradas en `validations` tienen `user_uid` distintos.
