# Acceptance Tests — CU-01: Solicitar Parada a Puerta

**Feature:** F4 — StopRequestModule + MapScreenBuyer + MapScreenVendor + TrackingScreen
**SDD refs:** SDD_FASE4_UBISAFE.md §8.1.A/B/C · SDD_FASE2_PASO25_UBISAFE.md §5.3.3

---

## Precondiciones

1. Firebase emuladores corriendo:
   ```bash
   firebase emulators:start --project demo-ubisafe
   ```
2. API corriendo (con venv activado):
   ```bash
   cd ubisafe_api
   python -m pip install -r requirements.txt   # solo si no está hecho
   uvicorn main:app --reload
   ```
3. App en dos instancias Android (dispositivo físico o dos emuladores).
4. Si se usa dispositivo físico, ejecutar `adb reverse` para los 4 puertos:
   ```bash
   adb reverse tcp:9099 tcp:9099   # Auth emulator
   adb reverse tcp:8080 tcp:8080   # Firestore emulator (puerto 8080 — ver firebase.json)
   adb reverse tcp:9000 tcp:9000   # RTDB emulator
   adb reverse tcp:8000 tcp:8000   # FastAPI local
   ```
5. Dos cuentas de prueba creadas en el emulador de Auth (http://localhost:4000):
   - **Vendor V** (ej. `vendor@test.com`, rol = `VENDOR`)
   - **Buyer B** (ej. `buyer@test.com`, rol = `BUYER`)

## S1 — Flujo Normal (aceptación y entrega confirmada)

**Corresponde a:** SDD_FASE4_UBISAFE.md §8.1.A

| # | Actor | Acción | Resultado esperado |
|---|-------|--------|--------------------|
| 1 | Vendor | Iniciar sesión → `MapScreenVendor` | Pantalla del mapa del vendedor |
| 2 | Vendor | Tocar **"Activar Visibilidad"** → confirmar diálogo | Badge "Visible" en AppBar. En RTDB emulador (`http://localhost:4000`): `/vendedores_activos/{uid}` con `lat`, `lng`, `timestamp`, `activo: true` |
| 3 | Buyer | Iniciar sesión → `MapScreenBuyer` | Pantalla del mapa del comprador |
| 4 | Buyer | Observar mapa | Marcador verde del Vendor aparece en ≤ 5 s |
| 5 | Buyer | Tocar marcador del Vendor | Bottom sheet con nombre/info del Vendor + botón "Solicitar Parada" |
| 6 | Buyer | Tocar **"Solicitar Parada"** | `_WaitingOverlay` con spinner y countdown 60 s. En Firestore: `stop_requests/{id}` con `status: "pending"`, `buyer_uid`, `vendor_uid`, `expires_at` |
| 7 | Vendor | Recibir notificación FCM | Diálogo `_IncomingStopDialog` con coordenadas del Buyer |
| 8 | Vendor | Tocar **"Aceptar"** | Firestore `status: "accepted"`. Si `MAPS_API_KEY` configurado: polyline de ruta aparece en mapa del Vendor |
| 9 | Buyer | (automático al recibir FCM accepted) | `_WaitingOverlay` desaparece. App navega a `TrackingScreen`. Marcador azul del Vendor visible. Badge con distancia Haversine actualizado en tiempo real |
| 10 | Vendor | Tocar **"Confirmar Entrega"** en `_ConfirmDeliverySheet` | Firestore `status: "completed"` |
| 11 | Buyer | (automático al recibir FCM completed) | SnackBar "¡El vendedor llegó!". `TrackingScreen` regresa a `MapScreenBuyer` |

**Criterio de éxito:** secuencia de estados en Firestore: `pending → accepted → completed`. Sin crashes ni errores en consola.

## S3 — Timeout de 60 segundos

**Corresponde a:** SDD_FASE4_UBISAFE.md §8.1.C

| # | Actor | Acción | Resultado esperado |
|---|-------|--------|--------------------|
| 1–7 | — | Repetir S1 pasos 1–7 | Diálogo de solicitud en Vendor |
| 8 | — | **No tocar ningún botón** | Esperar 60 s |
| 9 | Sistema | Timer cliente (`StopRequestModule._startTimer`) expira | `PATCH /stops/{id}/status` con `status: "expired"`. Firestore `status: "expired"` |
| 10 | Buyer | (automático) | SnackBar "Tiempo de espera agotado." App permanece en `MapScreenBuyer` |
| 11 | Vendor | (opcional) Tocar "Aceptar" después del timeout | API devuelve `400 Bad Request` (transición `expired → accepted` no existe). SnackBar de error en Vendor. Sin crash |

**Criterio de éxito:** `status: "expired"` en Firestore. Buyer ve SnackBar de timeout. Intento tardío del Vendor es rechazado con 400.

## S4 — Race Condition (Buyer cancela vs Vendor acepta simultáneamente)

**Cobertura:** lógica 409 en `router.py` + manejo silencioso en `StopRequestModule`

| # | Actor | Acción | Resultado esperado |
|---|-------|--------|--------------------|
| 1–7 | — | Repetir S1 pasos 1–7 | Solicitud `pending` activa |
| 8a | Buyer | Tocar **"Cancelar"** en `_WaitingOverlay` | `PATCH expired` enviado |
| 8b | Vendor | Tocar **"Aceptar"** casi simultáneamente | `PATCH accepted` enviado |
| 9 | Sistema | El que llega primero gana | Si buyer ganó: `status: "expired"`, Vendor recibe 400. Si vendor ganó: `status: "accepted"`, Buyer recibe 409 que el cliente ignora silenciosamente y se redirige a TrackingScreen al recibir FCM |

**Criterio de éxito:** el sistema no queda en estado inconsistente. El 409 no produce un crash. Se puede verificar vía `curl`:
```bash
# Terminal Buyer
curl -X PATCH http://localhost:8000/stops/<id>/status \
  -H "Authorization: Bearer <buyer_token>" \
  -H "Content-Type: application/json" \
  -d '{"status": "expired"}'

# Terminal Vendor (ejecutar casi simultáneamente)
curl -X PATCH http://localhost:8000/stops/<id>/status \
  -H "Authorization: Bearer <vendor_token>" \
  -H "Content-Type: application/json" \
  -d '{"status": "accepted"}'
```
